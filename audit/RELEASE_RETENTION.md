## معنى «مرخصة»

الاعتماد هنا **اعتماد حقوقي للتوزيع وفق سجل المصادر**، وليس إعادة ترخيص كل المحتوى برخصة واحدة:

- الكود الأصلي للمشروع تحت MIT.
- نصوص القرآن والتفاسير والترجمات والتلاوات والخطوط والأيقونة والبيانات الخارجية لا تدخل تلقائيًا في MIT؛ تظل تحت شروط أصحابها ومصادرها المسجلة في `DATA_PROVENANCE.md` و`THIRD_PARTY_REVIEW.md` وإشعارات الطرف الثالث.
- التفاسير محصورة في التراث المسموح والطبعات الخمس المدققة؛ الكتب الحديثة أو غامضة الحقوق محجوبة.
- أي إصدار لاحق يجب أن يجتاز بوابة الحقوق والبصمات والاختبارات نفسها؛ هذا القرار لا يبيح إضافة محتوى جديد بلا تدقيق.

## قواعد الاحتفاظ وعدم الاستبدال

1. **ممنوع حذف** أي Release أو tag أو asset مدرج أعلاه.
2. **ممنوع استبدال** ملف داخل إصدار منشور أو تحريك وسمه إلى commit آخر.
3. إذا ظهر خلل، يُنشر إصدار جديد برقم جديد، وتُذكر النسخة السابقة على أنها superseded من دون حذفها.
4. انتقال قناة التحديث إلى إصدار أحدث لا يزيل الإصدار السابق ولا أصوله.
5. لا يجوز لأي workflow أو سكربت تنفيذ GitHub Release DELETE أو حذف وسم إصدار منشور.
6. GitHub Actions artifacts المؤقتة ليست بديلًا عن Release assets؛ الأصول النهائية وبصماتها يجب أن تبقى داخل GitHub Release.
7. تُفعّل خاصية **Immutable Releases** في المستودع قبل نشر Android `1.4.0` وكل إصدار لاحق. تُنشأ الإصدارات Draft أولًا، وتُرفع كل الأصول، ثم تُنشر مرة واحدة.
8. الأداة `scripts/lock_approved_releases.py` هي المسار المدقق لتفعيل الإعداد وقفل الإصدارات الثلاثة المنشورة أعلاه؛ تقرأ الرمز من متغير بيئة مؤقت ولا تحفظه.

## الحد التقني

GitHub Release Immutability تمنع تعديل/حذف الأصول وتحريك الوسم بعد النشر، لكنها لا تلغي قدرة مدير المستودع على حذف الإصدار كاملًا في بعض الحالات. لذلك يجتمع القفل التقني مع قرار المالك الدائم أعلاه. أي حذف إداري يخالف هذه السياسة صراحةً.
